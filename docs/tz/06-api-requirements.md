# Только для решений с собственным API

Источник: стр. 10 PDF.

Раздел с условным применением. Наличие собственного API не обязательно и само по себе не даёт
дополнительных баллов (ограничение 6). Требования ниже действуют, только если команда заявляет
собственный API на проверку.

---

## Что нужно предоставить

### 1. Адрес проверяемого API

> Полный HTTPS-адрес, доступный в течение периода проверки.

### 2. OpenAPI 3.0 или 3.1

> Файл `openapi.yaml` или `openapi.json` с описанием методов и форматов.

### 3. Тестовые учётные записи

> Для ролей, необходимых для проверки обязательных сценариев. Административный доступ
> предоставляется только при необходимости.

### 4. Тестовые данные

> JSON, CSV или иной согласованный формат, необходимый для воспроизводимой проверки.

### 5. `DATA-API.yaml`

> `DATA-API.yaml`, содержащий:
>
> 1. **версию конфигурации** (версию схемы файла, по которой платформа оценки будет выполнять
>    проверку);
> 2. **наименование решения или идентификатор команды** (название решения или идентификатор
>    команды);
> 3. **базовый адрес API** (единый HTTPS-адрес, относительно которого формируются запросы);
> 4. **перечень обязательных проверок** (перечень методов, которые относятся к основной
>    функциональности);
> 5. **HTTP-метод** (GET, POST, PUT, PATCH или DELETE) и относительный путь эндпоинта;
> 6. **параметры запроса** (query-параметры, path-параметры, заголовки и тело запроса);
> 7. **роль пользователя** (роль тестовой учётной записи, необходимая для выполнения проверки);
> 8. **ожидаемые статус-коды** (допустимые коды ответа для конкретного запроса);
> 9. **ожидаемый формат ответа** (тип содержимого, JSON-структуру и обязательные поля).

---

## Решение команды: API на проверку по умолчанию не заявляем

Внутренний REST между бэкендом на C# и мини-приложением на React — **не то же самое**, что
«решение с собственным API» в смысле этого раздела. Заявлять API на проверку — отдельное
осознанное решение.

**Против:**

- Баллов за сам факт наличия API нет (ограничение 6).
- Появляются два новых способа потерять баллы. В критерии «Работоспособность и полнота основных
  функций» (18% итога) добавляется пункт «для решений с собственным API обязательные проверки
  API проходят корректно». В критерии «Корректность интеграции» (12% итога) — пункт «статус-коды,
  форматы данных, заголовки и обязательные поля соответствуют заявленному контракту».
- Нужен публичный HTTPS-адрес, живой **весь период проверки**, плюс тестовые учётки и
  синхронный с кодом `openapi.yaml` и `DATA-API.yaml`.

**За:** ничего, кроме случая, когда API сам по себе является продуктовой ценностью решения
(например, мы позиционируем его как интеграционный слой для УК).

**Итог:** заявляем API, только если он становится частью продуктовой истории. Решение
пересматриваем в Фазе 4, не позже. Если заявляем — `openapi.yaml` и `DATA-API.yaml` попадают
в [../checklists/02-submission.md](../checklists/02-submission.md) как обязательные артефакты.
