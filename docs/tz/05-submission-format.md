# Формат сдачи

Источник: стр. 9–10 PDF, раздел «Обязательно для всех решений».
Требования к решениям с собственным API вынесены в [06-api-requirements.md](06-api-requirements.md).

Чек-лист для прогона перед сдачей — [../checklists/02-submission.md](../checklists/02-submission.md).

---

## 1. Работающее решение в MAX

> Ссылка или иной способ доступа к чат-боту или мини-приложению для прохождения основного
> сценария.

## 2. Зафиксированная версия исходного кода

> Git-репозиторий с **commit hash** или архив с контрольной суммой. После дедлайна версия не
> изменяется. Возможность внесения изменений в код и презентацию продукта появится только у
> финалистов после объявления результатов онлайн-этапа.

## 3. README.md

> README.md должен содержать:
>
> - назначение решения;
> - основной пользовательский сценарий;
> - состав и архитектуру решения;
> - одну команду для запуска всех локальных компонентов решения через Docker;
> - необходимые параметры окружения;
> - переменные окружения;
> - используемые порты;
> - зависимости;
> - внешние сервисы и интеграции;
> - описание работы с данными;
> - порядок работы с тестовыми данными;
> - пошаговый сценарий проверки;
> - примеры ожидаемого поведения системы;
> - известные ограничения;
> - порядок остановки и повторного запуска решения.

Дополнительно:

> Если для работы MVP необходим внешний сервис, который невозможно воспроизвести внутри Docker,
> отдельно укажите его назначение и условия, необходимые для проверки решения.
>
> Контейнеризация **не заменяет** работающую версию продукта в MAX: чат-бот или мини-приложение
> должны оставаться доступны для прохождения основного пользовательского сценария.

В списке 15 буллетов, хотя «необходимые параметры окружения» и «переменные окружения» на
практике закрываются одним разделом. Сверяемся по
[../checklists/02-submission.md](../checklists/02-submission.md): потерянный пункт стоит баллов
по критерию «Техническая документация и комплектность».

## 4. Файл зависимостей

> Например, `requirements.txt`, `package-lock.json` или другой файл, фиксирующий используемые
> библиотеки и версии.

## 5. Docker-конфигурация

> Решение должно быть подготовлено для воспроизводимого запуска в Docker.
>
> В репозитории должны находиться:
> - **Dockerfile** для компонентов решения, которые необходимо запускать локально;
> - **compose.yaml** или **docker-compose.yml**, позволяющий запустить все необходимые локальные
>   компоненты решения **одной командой**;
> - **.dockerignore**;
> - **.env.example** без рабочих токенов, паролей и ключей.
>
> Готовый Docker-образ может быть дополнительно размещён в Docker Hub или другом сервисе, однако
> наличие готового образа не заменяет файлы, необходимые для воспроизводимой сборки решения из
> переданного исходного кода.
>
> Сборка решения в Docker должна занимать **не более 5 минут** (без учёта первоначальной загрузки
> базовых Docker-образов). Docker-конфигурация должна содержать только необходимые для запуска
> компоненты и зависимости и не включать избыточные операции, существенно увеличивающие время
> сборки.

Наши решения по Docker — [../tech/05-docker-and-runtime.md](../tech/05-docker-and-runtime.md).

## 6. Презентация решения в формате PDF

> Структура презентации может отличаться, однако материалов должно быть достаточно для
> продуктовой оценки.

### Первый слайд — служебный

> Первый слайд — техническая информация для проверки. Укажите:
>
> - ссылку на работающего чат-бота или мини-приложение в MAX;
> - ссылку на Git-репозиторий и commit hash;
> - адрес собственного API, если используется;
> - тестовые логины и пароли;
> - рабочие токены, API-ключи и другие значения переменных окружения, необходимые для запуска и
>   проверки решения;
> - краткий порядок прохождения основного пользовательского сценария.
>
> Первый слайд служебный и не оценивается в рамках продуктовой презентации. Данные с него
> используются только для технической проверки решения.

Рабочие токены и ключи нельзя класть в репозиторий (ограничение 8), но нужно указать на
служебном слайде презентации. Это единственное место, где они передаются проверяющим.

### Со второго слайда — продуктовая часть

> Начиная со второго слайда, рекомендуем раскрыть:
>
> - название решения и состав команды;
> - executive summary (резюме проекта);
> - целевую аудиторию, проблему и её актуальность;
> - решение и основной пользовательский сценарий;
> - ожидаемый эффект;
> - архитектуру решения;
> - используемые данные и интеграции;
> - потенциал масштабирования и условия адаптации решения;
> - ограничения, риски и ключевые допущения;
> - использованные источники.

Разложено по слайдам с привязкой к критериям — [../product/07-presentation-outline.md](../product/07-presentation-outline.md).
