# Модель данных

**Статус:** ⬜ не заполнено · **Срок:** Фаза 2 (18—22.09) · **Отвечает:** Слава

Базовая модель данных входит в **ядро продукта** — то, что не меняется при масштабировании
([../product/05-scaling.md](../product/05-scaling.md)). Проектируем её так, чтобы перенос
в другой дом, УК или регион не требовал изменения схемы.

---

## Дом-ядро

Общая часть для всех трёх модулей: без неё ни один из них не работает.

### Сущности

| Сущность | Назначение | Источник данных |
|---|---|---|
| `Address` | адрес, нормализованный по ФИАС | ФИАС / ФНС |
| `Building` | многоквартирный дом: характеристики, год, серия, этажность | ГИС ЖКХ (или тестовые данные) |
| `ManagingOrganization` | УК / ТСЖ, реквизиты, контакты | ГИС ЖКХ (или тестовые данные) |
| `Premise` | помещение в доме | |
| `User` | пользователь MAX | MAX |
| `UserBuildingLink` | привязка пользователя к дому и роли | наша |
| `Role` | житель, собственник, председатель совета МКД, сотрудник УК | наша |

### Ключевое решение: идентификация дома

Привязка пользователя к конкретному МКД — фундамент всего продукта. Варианты:

| Способ | Плюсы | Минусы |
|---|---|---|
| Ввод адреса с подсказками по ФИАС | универсально, официальные данные | нужен справочник, нормализация |
| Выбор из списка домов УК | просто | работает только для подключённых УК |
| Код от УК / QR в подъезде | подтверждает принадлежность | требует участия УК |

**Выбранный способ:** ______________
**Как подтверждается, что пользователь действительно живёт в этом доме:** ______________

Подтверждение принадлежности важно и для безопасности (доступ к данным соответствует логике
решения), и для пилота. Для MVP допустимо упрощение, но оно должно быть заявлено в ограничениях.

## Переменная часть — в справочниках, не в коде

Всё, что различается между регионами, УК и типами домов, лежит в БД или конфигурации.
Проверочный вопрос: *чтобы запустить в другом регионе, менять код или данные?*

| Справочник | Что хранит | Пример различий между контекстами |
|---|---|---|
| Категории обращений | типы проблем | разные у разных УК |
| Зоны ответственности | кто отвечает за категорию: УК / РСО / подрядчик / муниципалитет | зависит от региона и формы управления |
| Нормативные сроки | сроки рассмотрения и устранения | нормативка + региональные акты |
| Тарифы и нормативы | | региональные |
| Тексты и формулировки | | брендирование под УК |

## Состояние диалога

Хранится в БД, не в памяти процесса.

Причина — подпункт критерия «Стабильность работы»: «после ошибки пользователь может продолжить
работу **без полного перезапуска решения**». Перезапуск контейнера не должен терять контекст
пользователя.

| Что храним | Зачем |
|---|---|
| Текущий шаг сценария | продолжение после сбоя |
| Введённые данные | возврат к ранее введённому |
| Последнее действие | обработка повторных нажатий |

## Происхождение данных — требование к схеме

Принцип 3 из [../tz/11-official-data.md](../tz/11-official-data.md): пользователь должен
понимать происхождение результата. Это влияет на схему, а не только на UI.

У каждой записи, показываемой пользователю, должны быть поля:

| Поле | Значения |
|---|---|
| `source` | официальный источник / расчёт продукта / рекомендация / тестовые данные |
| `source_name` | ГИС ЖКХ, ФИАС, УК, наш расчёт… |
| `actual_at` | дата актуальности |
| `territory` | территория, к которой относятся данные |

Без этих полей невозможно выполнить требование «как пользователь узнает источник и дату
актуальности» — и невозможно честно пометить демо-данные в интерфейсе.
