## Обязательные файлы

| Файл | Назначение | Готово |
|---|---|---|
| `Dockerfile` | для каждого компонента, запускаемого локально | ⬜ |
| `compose.yaml` | запуск **всех** локальных компонентов **одной командой** | ⬜ |
| `.dockerignore` | | ⬜ |
| `.env.example` | **без рабочих токенов, паролей и ключей** | ⬜ |
| файл зависимостей | `packages.lock.json`, `package-lock.json` — с зафиксированными версиями | ⬜ |

> Готовый образ в Docker Hub можно выложить дополнительно, но он **не заменяет** файлы для
> воспроизводимой сборки из переданного исходного кода.

## Бюджет сборки: 5 минут

> ТЗ: сборка не более 5 минут без учёта первоначальной загрузки базовых образов. Конфигурация
> должна содержать только необходимые компоненты и не включать избыточные операции.

**Замер:** `____ мин` (дата: ________)

Как уложиться:

- [ ] Многоступенчатая сборка (`build` → `runtime`), в финальный образ не тянется SDK
- [ ] Слои упорядочены по изменяемости: восстановление зависимостей отдельным слоем до
      копирования исходников (`*.csproj` → `dotnet restore` → остальной код)
- [ ] `package.json` / lock-файл копируются до остального фронта
- [ ] `.dockerignore` исключает `bin/`, `obj/`, `node_modules/`, `.git/`, артефакты тестов
- [ ] Тесты и линтеры не гоняются внутри образа для сдачи
- [ ] Нет установки лишних системных пакетов

## Состав `compose.yaml`

| Сервис | Образ / сборка | Порт | Зависит от |
|---|---|---|---|
| `api` | сборка из `./src/Api` | | `db` |
| `web` | сборка из `./src/Web` | | `api` |
| `db` | `postgres:` (зафиксировать версию) | | — |

- [ ] Версии базовых образов зафиксированы тегами, не `latest`
- [ ] `depends_on` + healthcheck: `api` не стартует раньше готовности БД
- [ ] Миграции БД применяются автоматически при старте
- [ ] Тестовые данные загружаются автоматически при старте
- [ ] Всё поднимается **одной командой**

**Команда запуска:** `docker compose up -d --build`

## Внешние сервисы вне Docker

> ТЗ: «Если для работы MVP необходим внешний сервис, который невозможно воспроизвести внутри
> Docker, отдельно укажите его назначение и условия, необходимые для проверки решения».

| Сервис | Зачем нужен | Что нужно проверяющему |
|---|---|---|
| MAX (мессенджер) | среда работы продукта | доступ к боту по ссылке со служебного слайда |
| | | |

Контейнеризация не заменяет работающую версию продукта в MAX: бот и мини-приложение должны
оставаться доступны для прохождения основного сценария независимо от того, поднял ли
проверяющий Docker.

## Прогон с нуля

Делается на машине, где проект никогда не собирался. В Фазе 2 — первый раз, дальше в конце
каждой фазы.

1. [ ] `git clone` в пустую папку
2. [ ] `cp .env.example .env`, заполнены только переменные, описанные в README
3. [ ] Одна команда — всё поднялось
4. [ ] Замерено время сборки: ____ мин
5. [ ] Сценарий проверки из README пройден по шагам
6. [ ] Результат совпал с «примерами ожидаемого поведения» из README
7. [ ] Остановка по инструкции из README
8. [ ] Повторный запуск по инструкции — данные на месте, сценарий проходится снова
