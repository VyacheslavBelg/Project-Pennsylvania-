**Статус:** черновик, уточняется в Фазе 2 · **Отвечает:** Слава

Закрывает критерий «Техническая реализация и архитектура» (20% техблока, **12% итога**) и
питает слайд «Архитектура решения».

## Стек

ТЗ, ограничение 4: «Для работы с мессенджером MAX советуем использовать JavaScript и React.
**Допускается использование других языков программирования и API**». C# на бэкенде разрешён.

| Слой | Технология | Обоснование |
|---|---|---|
| Бэкенд, бот, бизнес-логика | **ASP.NET Core (C#)** | основная компетенция команды; допускается ТЗ |
| Хранилище | **PostgreSQL** | справочники и переменная часть в БД, а не в коде |
| Мини-приложение | **React + TypeScript** | рекомендовано ТЗ |
| UI-компоненты | **MAX UI** | React-библиотека в стилистике MAX |
| Интеграция с платформой | **MAX Bridge** | платформа запуска (iOS/Android/desktop/web), API устройства |
| Запуск | **Docker + Compose** | требование формата сдачи, одна команда |

Подпункт критерия: «выбранные технические решения соответствуют заявленной функциональности».
Жюри спросит, почему C#, а не рекомендованный JS. Ответ: компетенция команды, скорость
разработки, мини-приложение на React там, где это требуется платформой.

                    └──────┬────────────────┬───────┘
                           │                │
                    ┌──────▼─────┐   ┌──────▼────────┐
                    │ PostgreSQL │   │ справочники,   │  ← переменная часть
                    │            │   │ конфигурация   │
                    └────────────┘   └───────────────┘

Схему уточнить в Фазе 2 и перерисовать для презентации читаемо.

| Компонент | Роль | Запускается локально в Docker |
|---|---|---|
| `bot` (ASP.NET Core) | приём webhook от MAX, сценарии чата, отправка сообщений | да |
| `api` (ASP.NET Core) | REST для мини-приложения, бизнес-логика модулей | да |
| `web` (React) | мини-приложение | да |
| `db` (PostgreSQL) | данные и справочники | да |

Объединять ли `bot` и `api` в один сервис — решается в Фазе 2. Для масштаба MVP один сервис
проще: критерий требует, чтобы «структура решения была логична и соответствовала масштабу MVP».
Микросервисы ради микросервисов работают против него.

## Граница «ядро / переменная часть»

Ключевое архитектурное требование — оно закрывает сразу два критерия: архитектуру (12% итога)
и масштабирование (14% итога). Подробнее — [../product/05-scaling.md](../product/05-scaling.md).

**В ядре:** идентификация дома, модель данных, роли пользователей, механика сценариев,
каркас интерфейса.

**В переменной части (конфигурация и справочники в БД, не `if`-ы в коде):** региональные
нормативы и сроки, правила маршрутизации обращений по зонам ответственности, справочники
организаций, реквизиты интеграций, тексты и формулировки.

Проверочный вопрос: *чтобы запустить продукт в другом регионе, нужно менять код или данные?*
Если код — граница проведена неправильно.

## Разделение сценария между чатом и мини-приложением

По критериям из [../tz/08-max-platform.md](../tz/08-max-platform.md), а не по удобству разработки.

| В чат-боте | В мини-приложении |
|---|---|
| вход и привязка к дому | карточка дома |
| короткие регулярные действия | списки, каталоги, документы |
| уведомления и напоминания | сложные формы |
| проверка статуса | сравнение объектов |
| выбор из небольшого числа опций | возврат к ранее введённым данным |

**Ограничение 5 ТЗ:** мини-приложение подключается к чат-боту и не используется как
изолированный от него сервис. Точка входа — всегда бот.

**Ограничение 3 ТЗ:** функциональность доступна и в мобильной, и в веб-версии MAX.
Проверять в обеих по ходу разработки, не в конце. MAX Bridge даёт платформу запуска —
используем для адаптации, а не для урезания функций.

## Требования к коду от критериев оценки

| Подпункт критерия | Что делаем |
|---|---|
| «Понятны состав компонентов, их роли и связи» | структура решения повторяет схему выше; README описывает её же |
| «Ключевая логика разделена и организована так, чтобы решение можно было поддерживать» | ядро и модули — отдельные проекты/папки; переменная часть в конфиге |
| «Данные, состояния и результаты передаются предсказуемо» | единый формат ошибок API, явные состояния сценария |
| «После ошибки пользователь может продолжить без полного перезапуска» | состояние диалога в БД, а не в памяти процесса |
| «Отсутствуют систематические сбои, тайм-ауты» | таймауты и ретраи на исходящих вызовах MAX API |
