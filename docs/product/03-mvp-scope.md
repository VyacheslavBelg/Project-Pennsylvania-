# Границы MVP и выбор приоритетного сценария

**Статус:** ⬜ не заполнено · **Срок:** Фаза 1, до начала разработки модулей · **Отвечает:** вся команда

Методика — [../tz/10-problem-to-solution.md](../tz/10-problem-to-solution.md), шаг 4.

> **Определение MVP из ТЗ:** «MVP — это не уменьшенная версия большого продукта, а минимальная
> версия, в которой пользователь способен **полностью** получить основной результат.»

---

## Решение по объёму: один продукт, три модуля, один сквозной сценарий

Команда закрывает все три направления трека. Рекомендация 03 ТЗ просит обратного:
«Не пытайтесь охватить сразу все процессы управления домом — выберите участок… и реализуйте его
от начала до конца».

**Принятый компромисс:**

| Слой | Что это | Статус |
|---|---|---|
| **Дом-ядро** | Привязка пользователя к конкретному МКД (адрес → ФИАС → реквизиты дома и УК), общая модель данных, общая навигация, единый бот | Must Have |
| **Приоритетный модуль** | Один сквозной сценарий, работающий от начала до результата, без тупиков, с обработкой ошибок. Его демонстрируем и его проверяет жюри | Must Have |
| **Модуль 2** | Меньшей глубины, границы заявлены честно | Should Have |
| **Модуль 3** | Меньшей глубины, границы заявлены честно | Could Have |

**Правило приоритета, действующее до конца онлайн-этапа:** если приоритетный сценарий не
доведён до состояния «проходится целиком, повторно, чужим человеком» — режутся модули 2 и 3,
а не он. Обратный размен запрещён.

Обоснование: «работоспособность и полнота основных функций» весит 18% итога — больше любого
другого критерия. Три модуля по 60% готовности дают 0–1 балл по нему; один модуль на 100% плюс
два заявленных расширения дают 3.

**Как это защищается перед жюри:** дом-ядро — это и есть ответ на критерий масштабирования
(35% продуктовой оценки). Ядро переносится в новый дом, УК, муниципалитет и регион без
изменений; переменная часть — региональные данные, справочники, интеграции, роли. Три модуля
поверх общего ядра доказывают, что ядро действительно переиспользуемо.

## Выбор приоритетного модуля

### Критерии выбора

| Критерий | Вес для нас | Почему |
|---|---|---|
| Глубина проблемы для выбранного пользователя | высокий | критерий «Пользовательская ценность» |
| Реализуемость сквозного сценария за срок | высокий | критерий «Работоспособность», 18% итога |
| Возможность обойтись без недоступных интеграций | высокий | запрет имитировать интеграции |
| Измеримость эффекта | средний | критерий «Ожидаемый эффект» |
| Переносимость в другой контекст | средний | критерий «Масштабирование», 14% итога |
| Отличие от ГИС ЖКХ и «Решаем вместе» | средний | подпункт «преимущество перед текущим способом» |

### Оценка направлений

Заполнить в Фазе 1. Шкала 1–5.

| Направление | Глубина проблемы | Реализуемость | Без интеграций | Измеримость | Переносимость | Отличие от аналогов | Σ |
|---|---|---|---|---|---|---|---|
| Аварии, заявки и коммунальные услуги | | | | | | | |
| Жилищный навигатор: дом, капремонт, тарифы, документы | | | | | | | |
| Домовое сообщество, собрания, коммуникация с УК/ТСЖ | | | | | | | |

**Риск, который надо учесть отдельно:** направление «Аварии и заявки» требует соблюдать
установленный законом порядок работы с обращениями граждан (прямо оговорено в ТЗ, стр. 5).
Это ограничивает, что можно обещать пользователю по срокам и статусам.
