# Границы MVP и выбор приоритетного сценария

**Статус:** ⬜ не заполнено · **Срок:** Фаза 1, до начала разработки модулей · **Отвечает:** вся команда

## Решение по объёму: один сценарий, две поверхности

Зафиксировано 19.09.2026. Пересматривает более ранний вариант с тремя модулями.

Делаем **один сквозной сценарий** — обращение по бытовому сбою — и показываем его в двух
формах, которые работают на одном бэкенде:

| Слой | Что это | Статус |
|---|---|---|
| **Дом-ядро** | Привязка пользователя к конкретному МКД (адрес → ФИАС → реквизиты дома и УК), модель данных, роли | Must Have |
| **Чат-бот** | Основной сценарий: классификация проблемы, определение ответственного, нормативный срок, подача обращения, уведомления | Must Have |
| **Мини-приложение** | Карточка обращения: статус, таймер до истечения срока, ответственный, история, эскалация в ГЖИ | Should Have |
| Жилищный навигатор, домовое сообщество | Направления трека, которые мы **не реализуем** в этой версии | Won't Have |

### Почему мини-приложение обслуживает тот же сценарий, а не добавляет второй

Прямых баллов за наличие мини-приложения нет ни в одном критерии — форма решения не
оценивается, оценивается результат. Рекомендация 04 предупреждает: инструменты «должны помогать
решить проблему, а не становиться самоцелью».

Мини-приложение берётся по трём причинам, и ни одна из них не про охват:

- в команде есть фронтенд-разработчик, который иначе простаивает, и работает он параллельно,
  не отнимая время у бэкенда;
- визуальная демонстрация сильнее на защите — «Качество MVP и пользовательского опыта» весит
  12% итога финала;
- MAX Bridge открывает возможности для платформенного бонуса, недоступные чат-боту.

Карточка обращения попадает ровно в те случаи, которые документация MAX называет уместными для
мини-приложения: работать со списком, возвращаться к ранее введённым данным, одновременно
видеть несколько связанных элементов.

### Почему чат-бот, а не только мини-приложение

Документация MAX перечисляет шесть признаков, когда уместен чат-бот. Наш сценарий попадает
во все шесть: последовательные вопросы при классификации, выбор из небольшого числа опций,
персональный результат, проверка статуса, уведомления о сроке, короткое регулярное действие.

Это аргумент для защиты: чат-бот выбран не из экономии, а потому что сценарий чатовый.

### Правило приоритета до конца онлайн-этапа

Если сквозной сценарий в боте не доведён до состояния «проходится целиком, повторно, чужим
человеком» — режется мини-приложение, а не он. Обратный размен запрещён.

Обоснование: «работоспособность и полнота основных функций» весит 18% итога, больше любого
другого критерия. Сценарий на 100% плюс заявленное расширение даёт 3 балла; две половинки
дают 0–1.

### Что с масштабированием

Отказ от двух направлений не ослабляет критерий масштабирования — он про перенос в новый
контекст, а не про охват процессов. Дом-ядро переносится в другой дом, УК, муниципалитет и
регион без изменений; переменная часть — региональные справочники, нормативные сроки, зоны
ответственности, интеграции. Жилищный навигатор и домовое сообщество заявляются как
направления развития продукта — это и есть «реалистичный порядок тиражирования».

## Выбор приоритетного направления

Решено 19.09.2026: **«Аварии, заявки и коммунальные услуги в доме»**. Обоснование —
[01-problem-statement.md](01-problem-statement.md): обязанность УК принимать обращения через
MAX действует с 01.09.2026, а адресат, срок и статус пользователю по-прежнему неизвестны.

Таблица ниже сохранена как след принятого решения.

### Критерии выбора

| Критерий | Вес для нас | Почему |
|---|---|---|
| Глубина проблемы для выбранного пользователя | высокий | критерий «Пользовательская ценность» |
| Реализуемость сквозного сценария за срок | высокий | критерий «Работоспособность», 18% итога |
| Возможность обойтись без недоступных интеграций | высокий | запрет имитировать интеграции |
| Измеримость эффекта | средний | критерий «Ожидаемый эффект» |
| Переносимость в другой контекст | средний | критерий «Масштабирование», 14% итога |
| Отличие от ГИС ЖКХ и «Решаем вместе» | средний | подпункт «преимущество перед текущим способом» |

### Оценка направлений

Заполнить в Фазе 1. Шкала 1–5.

| Направление | Глубина проблемы | Реализуемость | Без интеграций | Измеримость | Переносимость | Отличие от аналогов | Σ |
|---|---|---|---|---|---|---|---|
| Аварии, заявки и коммунальные услуги | | | | | | | |
| Жилищный навигатор: дом, капремонт, тарифы, документы | | | | | | | |
| Домовое сообщество, собрания, коммуникация с УК/ТСЖ | | | | | | | |

**Риск, который надо учесть отдельно:** направление «Аварии и заявки» требует соблюдать
установленный законом порядок работы с обращениями граждан (прямо оговорено в ТЗ, стр. 5).
Это ограничивает, что можно обещать пользователю по срокам и статусам.

### Решение

**Направление:** «Аварии, заявки и коммунальные услуги в доме».
**Поверхности:** чат-бот — основной путь, мини-приложение — карточка обращения.
**Не делаем:** «Жилищный навигатор», «Домовое сообщество».
**Дата фиксации:** 19.09.2026, уточнено 20.09.2026 после разбора конкурентов.

**Обоснование:** обязанность УК принимать обращения через MAX действует с 01.09.2026, а зона
ответственности и применимый норматив жителю по-прежнему неизвестны — этого не закрывает ни
один существующий сервис. Разбор в [01-problem-statement.md](01-problem-statement.md).

Весь онлайн-этап уделяется этому направлению целиком.

### Won't Have — сознательно не делаем в этой версии

> ТЗ: «Для хакатона особенно важно определить последний блок. **Ограничение объёма — часть
> сильного продуктового решения.**»

| Что не делаем | Почему | Что потребуется, чтобы сделать потом |
|---|---|---|
| **Доставку обращения в систему УК** | канала в их системы нет, и создать его на хакатоне невозможно | интеграция с системой конкретной УК либо через ГИС ЖКХ |
| Реальную интеграцию с ГИС ЖКХ | нет доступа к системе | статус оператора или соглашение, см. [../tech/04-data-sources.md](../tech/04-data-sources.md) |
| Реальные данные о домах по всей стране | выгрузка ГИС ЖКХ недоступна | выгрузка реестра МКД по региону |
| «Жилищный навигатор»: капремонт, тарифы, документы | другой пользователь и другие данные; ГИС ЖКХ закрывает это из первоисточника | реестр работ и документов по региону |
| «Домовое сообщество»: ОСС, сбор позиций | отдельный процесс с собственным правовым порядком | проработка порядка проведения ОСС |
| Личный кабинет для сотрудников УК | вторая роль удваивает объём | договорённость с пилотной УК |
| Оплату, счётчики, домофон | закрыто «Госуслугами Дом», дублировать незачем | — |

**Самое важное ограничение — первое.** Мы формируем корректное обращение, определяем адресата
и считаем норматив, но **не доставляем обращение в систему УК**: житель отправляет его сам по
подсказанному каналу. Отсчёт срока ведётся от момента, когда пользователь подтвердил отправку.

Это прямо следует из принципа «не имитируйте интеграции» и должно быть заявлено в README,
в интерфейсе и на слайде данных — иначе читается как незаявленная недоделка.

Этот блок целиком идёт в презентацию на слайд «Ограничения, риски и ключевые допущения».
Незаявленное ограничение читается жюри как недоделка; заявленное — как решение.
